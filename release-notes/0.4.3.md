# TPS Calendar Base 0.4.3

## Intent

Make Calendar use GCM's authoritative checkbox/status mapping and prevent an unmapped Base status from silently changing a task to a guessed marker.

## Changes

- Removed Calendar's copied checkbox/status table and status-service fallback.
- Inline-task status resolution and Base-filter scheduling consume only GCM `taskCheckboxes` version 1.
- Custom markers, aliases, alternate markers, and uppercase `X` normalization follow the exact GCM result. Any valid one-character checkbox remains a structural task for Kind, title, tags, authored fields, and formulas; an unmapped marker receives no fabricated status/open/done aliases.
- Task-drop plans capture the exact source revision and one resolved marker. After confirmation, the mapping is checked again and one uniquely shifted unchanged line may be updated, while mapping changes, edited sources, malformed or unmapped markers, and ambiguous duplicates fail closed. The line patch applies scheduling metadata, clears only checkbox-owned workflow-status fields, and preserves a configured relational Status field.
- Task and dedicated-note creation resolve status through the same snapshot before target creation and revalidate it inside task-line append. The checkbox is the sole persisted line-level workflow carrier: no redundant `[status:: ...]` is written, and dedicated task-note frontmatter uses GCM's workflow key instead of a relational Status field.
- `row.status` remains authored row metadata, while `task.status`/`task.checkboxStatus` come only from the checkbox mapping. Rescheduling and task drops revalidate the live marker/mapping inside their atomic source callback.
- Inline-task parsing rejects empty, multi-character, and astral checkbox tokens rather than promoting them to todo. Existing unmapped one-character tasks remain visible, task-note/menu handoffs require a mapped token, and mapped event icons use the provider's configured icon.
- Mapped status remains readable when GCM's done classifier is unavailable, throwing, or non-boolean, but Calendar emits no completion aliases, excludes the task from completion filters, and does not dim it. Native and external records retain Calendar's standalone active/inactive status behavior.

## Compatibility and migration

- Backward-compatible patch; no settings, commands, Base definitions, note/task syntax, API versions, or stored-data migration.
- Minimum supported Obsidian remains 1.10.0.
- TPS Global Context Menu 1.17.1 is required for synthesized task-status behavior. Native note rows and external calendar events remain independent.

## Validation

- Focused regressions cover exact capability versioning, load order and replacement, mapped and unmapped custom markers, uppercase `X`, malformed/throwing providers, missing/throwing/contradictory done classification, inline-task-vs-native completion styling, structural Kind/formula preservation without workflow aliases, row-vs-task status namespaces, workflow/relational write ownership, mapped task creation, mapping changes before and during writes, stale/ambiguous drop rejection, unique line relocation, relational-status preservation, and fail-closed reschedule/drop/create mutation.
- The complete declared Calendar suite, TypeScript, mandatory separate production-mode build, and reloaded test-vault UI verification are recorded before publication.
- Test runtime state is preserved. Production is not accessed.

## Known limitations

- Inline task status aliases and workflow mutations are intentionally unavailable while GCM's mapping capability is missing, incompatible, or does not map that task's marker; structural task rows remain readable. When mapping succeeds but GCM cannot authoritatively classify completion, status remains readable while open/done/completed aliases, completion filters, and completion styling remain unavailable.
- A task cannot be scheduled through a Base status filter until that status has a configured GCM checkbox mapping.
