# TPS Calendar Base 0.16.1

Creating a calendar note no longer triggers an extra YAML rewrite after creation finishes. The removed canonicalization read an earlier snapshot, removed duplicate keys, reserialized formatting and then replaced the whole note. A concurrent editor change between that read and write could be lost. The initial creator already owns valid event frontmatter, so removing the redundant writer fixes the race at its source.

The unconditional 100 ms post-create delay is removed. An installed Obsidian Linter still runs once through `runLinterFile` or `lintFile`. Template preparation, Templater completion, template-instance marker handling, Calendar-owned fields, optional parent links and shared preview/open/stay routing retain their existing behavior. No retry, cache, observer, migration, new setting or automatic repair was added; existing malformed notes are untouched.

Patch release: backward-compatible creation correctness and performance fix. Minimum Obsidian remains **1.10.0**.

## Validation

- All four new lifecycle tests fail against 0.16.0 and pass with this fix.
- Both supported linter routes reproduced loss of a concurrent editor paragraph before the fix, and preserve exact formatting/body afterward.
- Ordinary no-template/no-parent/no-linter creation writes valid YAML once and performs zero follow-up raw/cached reads, mutations or timers. Previously it performed one raw read and queued a 100 ms delay.
- Templated creation retains Templater → one owned frontmatter merge → optional linter ordering with no second body writer.
- Focused creation suite: **36 passed**. Existing creation/open/mobile suite: **40 passed**. TypeScript and diff checks passed.

`TPS_NO_DEPLOY=1 npm test` against version 0.16.1 passed **305 checks, zero failures/skips**, including TypeScript and the production-mode build. The deployment helper reported `target=none reason=TPS_NO_DEPLOY`; the shared test runtime was preserved. The separate final `npm run build` deploys only shipped artifacts to Obsidian Plugin Test Vault. The installed version was reloaded by manifest ID; no runtime settings were replaced.

Installed lifecycle QA reproduced the 0.16.0 concurrent-edit loss through the real installed Calendar service with scoped call counters. On 0.16.1, ordinary creation and the linter/concurrent-edit scenario each made **one create, zero Calendar rereads and zero Calendar rewrites**, preserving the editor paragraph. Baseline samples took 9,734/12,113 ms; updated samples took 522/597 ms. Other TPS startup/indexing work was also improved during this coordinated run, so these timings describe the combined test-vault state and must not be attributed solely to Calendar. The operation counts isolate Calendar's own calls.

A separate installed check used the **real app and GCM registry**, created an Inbox event in 59 ms, and completed Calendar's configured editable-preview handoff through GCM 3.6.2. After 4.5 seconds the title, edited body and frontmatter remained intact; Calendar/GCM settings were unchanged. Synthetic fixtures are archived from Inbox after QA. This is a targeted creation check, not a production latency benchmark.

Tested in **Obsidian Plugin Test Vault** and ready for the user's **BRAT pull**. Native-record creation uses a separate unchanged route. Template/Templater sequencing is covered by regression tests; live Templater and physical iPhone interaction were not exercised. No production access, deployment or outbound provider calls were performed for this Calendar patch. Production installation and user acceptance remain separate.
