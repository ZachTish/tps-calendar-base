# TPS Calendar Base 3.0.2 — Reject task-free sources before reading bodies

Calendar's legacy historical-task discovery previously read every Markdown body initially and rescanned every body on every refresh. It now checks Obsidian's existing checklist metadata first, skipping known task-free notes before body reads, line splitting or parsing. Missing metadata stays eligible so newly synced notes are not silently excluded. Native-record mode already bypasses this legacy discovery and is unchanged.

Removed Calendar's duplicate per-view path/mtime/size body cache. Obsidian's existing `cachedRead` now owns freshness, so same-size/same-timestamp edits become visible on the next normal refresh. Existing eight-reader concurrency and per-source error isolation remain. Filename dates are not used to reject historical task sources: an old daily note can contain a future scheduled task. Base and formula filters retain their existing display ownership.

No setting, migration, listener, timer, watcher, cache, retry/repair system or automatic note writer is added. Controller storage defaults, external transport, creation and schedule-writing paths are unchanged. The runtime change removes more code than it adds. Backward-compatible patch, minimum Obsidian **1.10.0**. Settings navigation and mobile layout are unchanged.

## Validation

- All **378 declared tests** pass with zero failures, skips or cancellations, including TypeScript and the suite build. A separate final ordinary production build deployed only to **Obsidian Plugin Test Vault**. Targeted reload and installed manifest/source checks verified 3.0.2.
- Three new actual-method regressions fail on 3.0.1 and pass after the correction. Two task sources among 4,000 cached task-free notes now cause two reads/scans rather than 4,002. Fifty task-free refreshes perform zero body reads, line scans or writes rather than 5,000 line scans. Same-size/same-timestamp edits, missing metadata, task arrival/removal, rename/delete and cross-date task preservation are covered.
- An unmounted receiver using the installed class, synthetic host files/metadata/read boundary and a counting scanner confirms the same scope: 3.0.1 performs 4,002/4,002/4,002 scans over three passes; 3.0.2 performs 2/2/2. No write attempts. These are operation counts, not full-parser or device timings.
- Integrated backend-driven Bases checks used the real installed parser, rendering owner and enabled Test-vault TPS consumers over **21,289 Markdown files**. Two legacy discovery passes scanned **42,578 bodies before and 238 after** (119 eligible sources per pass), a 99.4% reduction. Vault cached-read calls across all enabled consumers were 21,293 before and 242 after; inventories remained two. Both samples made zero `modify`/`process` attempts. Scanner synchronous totals were approximately 11.36 s before and 0.68 s after; async discovery totals were 12.57 s and 1.04 s. These diagnostic sums are not end-to-end opening latency or mobile benchmarks. Window visibility was visible but focus false in these samples; final foreground interaction was not performed at the user's request. The before Base used a note-frontmatter fixture filter, while the final folder filter also admits historical task rows; the comparison is discovery work over the same source inventory, not identical query/render speed.
- The final installed Base displays all four fixture events: two whole notes, one undated historical task and a future task stored in a 2020 daily note. Separate installed collection finds both historical task rows through the real GCM line metadata contract. Only Calendar's storage-mode getter was temporarily forced to legacy; the original native-record mode was restored. There were zero external calendar sources; outbound automation stayed off.
- All twelve fixture Markdown sources and ten settings/state files remained byte-identical. Probes, method wrappers and mode overrides were removed, the QA folder archived directly, and the prior Test leaf restored. Final runtime is 3.0.2. Production was not accessed or deployed.

## Acceptance and rollback limits

Test-vault validated and ready for the user's **BRAT pull**. The user's reported physical-iPhone startup, touch, background/sync state and selected storage mode remain unverified; this patch fixes a demonstrated legacy bottleneck and does not establish complete resolution of device-specific lag. Known task-bearing files are still scanned on refresh, and the metadata-only Markdown inventory remains. Core Bases queries, external calendars and other consumers retain their own costs. Missing checklist metadata can temporarily keep more sources eligible. No new cache or background maintenance is introduced to conceal those costs.

No settings or note migration is required. Rolling back to 3.0.1 restores the former scans and duplicate body-cache behavior; this release does not rewrite notes or private state. Physical-device acceptance and production installation remain separate from this public release.
