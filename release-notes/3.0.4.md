# TPS Calendar Base 3.0.4 — Prepare visible event content

Backward-compatible performance and query-correctness patch. Minimum Obsidian: **1.10.0**. Tested in the isolated Obsidian Plugin Test Vault; ready for the user's BRAT pull after publication. This is not a production installation or a claim of half-second iPhone reopening.

## Changes

- Check configured date intervals before resolving titles, style rules, icons, timer classes and event models. Ordinary native-record presentation is restricted to the displayed range with an adjacent-day buffer. Navigation bounds still include all matching intervals. Navigation and real metadata changes recompute candidates without a retained cache.
- Reuse the existing interval logic for formula dates, duration/all-day rules, spanning events, auxiliary date pairs and pending edits. Filename dates do not override configured properties.
- Consume the public `BasesView.data` result after Core applies filtering, sorting and limits. Remove private in-progress query result fallbacks, the missing-data polling loop and its fabricated empty result. Core data notifications and the existing visible-resize lifecycle own readiness.
- Use FullCalendar 6's DOM-content interface for event cards, eliminating the separate React portal commit and another geometry pass. Preserve literal titles, icons, paths, native property value rendering, preview labels, context menus and drag handlers. All-day cards skip property widgets that were constructed and discarded.
- Remove three general startup sizing timers, a duplicate delayed measurement/header callback and the extra 120 ms data-notification wait. Keep actual resize work coalesced through the existing observer. Skip irrelevant time-grid slot sizing in month view and avoid repeating FullCalendar's initial mount measurement. Preserve existing embedded/canvas reveal sizing.
- Keep external-feed identity matching on its complete local inventory: notes moved outside the displayed interval must still suppress linked external events. Legacy historical task discovery is unchanged.

No new settings, dependencies, persistent state, watcher, poller, cache, repair system, note writer or migration. The runtime source removes 253 net lines. Settings destinations and defaults are unchanged.

## Validation

The final version passes **398** declared regression checks, TypeScript and a mandatory separate production-mode build. Stable deployment targets only the Test vault. Reload is by manifest ID `tps-calendar-base`; Hot Reload also reports disable/enable. No production artifact is deployed by this release task.

Regression coverage includes 3,676-date candidate selection, new visible ranges and metadata edits, spanning/formula/auxiliary intervals, archive exclusions, no fabricated dates, public query result ownership/limits/empty results, hidden/detached lifecycle, zero missing-data retry work, 50-notification coalescing, unchanged-size bursts, actual resize/cleanup and native card content/property behavior. Host timers, DOM and widget boundaries are mocked in focused tests; the installed checks below use the actual enabled consumers.

Installed Obsidian 1.14.4 on macOS, native-record mode, all 11 pre-existing community consumers enabled; Test Sync disabled and no external Calendar endpoints configured:

| Work over one 3,676-result month opening | 3.0.3 diagnostic | 3.0.4 final-source diagnostic |
| --- | ---: | ---: |
| Title/style/timer-class preparation calls each | 7,352 | 341 |
| Populated presentation passes | 2 | 1 |
| Final visible month events | 339 | 339 |
| Calendar event models retained | 3,676 | 341 |

The counters are separate from timings. Core still enumerates the vault once; its metadata/filter work is not eliminated. First-after-final-reload and repeated instrumented openings measured **2,324.2 ms** and **2,203.3 ms** to the complete month. Both retain one populated presentation pass, 341 title/style/timer preparations, one Core vault enumeration and no observed mutation calls. The diagnostic wrapped all metadata/read boundaries, so this is not interchangeable with an uninstrumented native sample. A foreground native Back/Forward opening, with Developer Tools closed and no CPU profiler, measured **1,221.4 ms** from Calendar factory to all 339 event nodes; public query data arrived at **383.7 ms**, the populated Calendar data pass took **64.8 ms**. A foreground native week opening measured **690.5 ms** to all 77 event nodes; query arrival **431.7 ms**, populated pass **36.1 ms**. These are individual desktop samples, not percentiles, cold app launches, click-to-paint measurements or iPhone acceptance. Input/transport before the view factory is excluded. Earlier interim candidates and a Calendar-CSS-disable experiment are not final acceptance; disabling Calendar CSS did not improve the result and no stylesheet change was made.

Native UI checks preserve the October month, November navigation (96 events), week (77 events), GCM context actions and a Reading-view embed with overflow expansion. All 3,677 pre-existing synthetic Markdown fixture hashes and nine plugin settings files remain unchanged; temporary notes are archived and diagnostics removed before handoff. No production settings or notes were used for this QA.

## Remaining performance limits

The requested **under-500 ms physical-iPhone reopening target is not met or verified by these desktop results**. Core Bases still performs its initial query, and FullCalendar still measures event segments within the displayed grid, including overflow rows. This change defers off-range presentation; it does not provide complete virtualization of every hidden in-range segment. Legacy feeds keep their full identity-matching work. iPhone Sync delivery, loaded version, real touch/navigation timing and background/reopening behavior require separate device acceptance and an explicitly authorized direct installation, or the user's normal BRAT update.
